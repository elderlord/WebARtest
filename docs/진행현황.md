#### 배포 트러블슈팅 기록 (백색 화면 3종, 원인이 각각 달랐음)

| 증상 | 원인 | 수정 |
|---|---|---|
| 완전 백지 | vite `base: './'` → 끝 슬래시 없는 URL에서 자산이 루트로 새어 404 | `base: '/WebARtest/'` 절대경로 고정 |
| 백지(부팅문구 잔존) | 자산 파일명 해시가 매 빌드 변경 + Pages가 HTML을 max-age=600 캐시 → 캐시된 옛 HTML이 삭제된 해시 파일 참조 | 파일명 해시 제거(`assets/index.js` 고정) |

### 0-A 런타임 게이트 — **통과** (2026-08-07, 실기기 iOS Safari)

CDN 런타임으로 다음이 실기기에서 모두 확인됨:
XR8 로드 → chunk 로드(XrController 확보) → three.js 연결 → **카메라 기동**.

실측으로 밝혀진 사실(문서만으로는 알 수 없던 것):

| 발견 | 내용 |
|---|---|
| **트래킹 모듈은 chunk에** | core `xr.js`에는 `run/loadChunk/version/featureFlags/CanvasScreenshot/MediaRecorder`만. **`XrController`는 chunk에 있어 이미지 타겟만 쓰려 해도 chunk 로드 필수.** `GlTextureRenderer`·`Threejs`는 core에 존재 |
| **SLAM 토글 지점 정정** | "chunk 미로드 = 이미지타겟 단독"은 **틀림**. 올바른 축은 `XrController.configure({disableWorldTracking})` → 0-B=true(타겟 단독) / 0-B2=false(SLAM) |
| `window.THREE` 필요 | `XR8.Threejs` 파이프라인 모듈이 전역 THREE를 요구. ES 번들 three를 전역 노출해야 함 |
| 캔버스 크기 수동 처리 | `XRExtras.FullWindowCanvas` 미사용 시 드로잉 버퍼가 기본 300x150이라 카메라가 화면 일부에만 그려짐 → 뷰포트에 맞춰 직접 리사이즈 |

#### 셰이더 스모크 — **PASS** (shimmer 경로 유효)

`?smoke`에서 카메라 텍스처를 커스텀 프래그먼트 셰이더로 샘플·변조 성공.
→ **shimmer(일렁임) 살아있음.** 1단계에서 글로우와 A/B 비교 가능(원 계획 유지).

| 확정 | 내용 |
|---|---|
| 카메라 텍스처 위치 | **`frameStartResult.cameraTexture`** |
| `processGpuResult` 모양 | `{gltexturerenderer:{viewport,shader}, reality}` — **텍스처 없음** |
| 조회 시점 | `onProcessGpu`가 아니라 **`onUpdate`/`onRender`** (전자는 결과 생산 단계) |
| UV 방향 | 카메라 텍스처는 위→아래 저장 → 셰이더에서 **v 뒤집기 필요** |

**남은 0-A 항목**: world scale calibration(폭 아는 타겟 50/100/150cm) — 0-B에서
임시 인쇄 타겟과 함께 수행하는 것이 효율적.

### 0-B 진행 (2026-08-08, 모니터 표시 타겟)

**성공**: 타겟 인식, found/updated/lost 이벤트, 정합박스 부착 모두 동작.

#### 스케일 규약 확정 (실측)

| 항목 | 확정 내용 |
|---|---|
| 정규화 방식 | 엔진은 **타겟 높이를 1단위로 정규화**. `sh=1.000`, `sw=0.750`(=크롭 가로세로비 1/1.333) |
| **실제 크기** | **`scaledWidth·scale` × `scaledHeight·scale`** — 스펙 §6.3 정정: `scale`을 적용해야 맞다(두 후보 동시 표시로 육안 판정, 자홍=적용 쪽이 인쇄 테두리와 일치) |
| world scale | `metersPerUnit = 실폭 / (scaledWidth·scale)`. A4로 검증 시 크롭 높이 280mm와 정확히 일치 |

#### 측정값 (모니터 표시, 실물 인쇄 아님)

| 항목 | 값 |
|---|---|
| 거리 | 50~62 cm (환산 후 실제와 부합) |
| 기울기 | 2~8° |
| **Pose 변동** | **1.5~2.5 mm** — 제목급 글자 기준 여유 있음 |
| FPS | 58~64 |

#### 스케일 규약 최종 확정 (k=1.000에서 인쇄 테두리와 일치)

타겟 v2(인쇄 테두리 = 추적 영역)로 재측정한 결과 **보정 없이(k=1.000)** 정합박스가
인쇄 테두리와 일치. 최종 규약:

> **타겟 크기 = `scaledWidth·scale` × `scaledHeight·scale`**
> `scaledWidth/Height`는 높이=1로 정규화된 치수, `scale`이 실제 배율.

또한 엔진 trackable region은 **3:4/4:3 고정**(luminance 480×640)이라 A4 전체(1.414)는
타겟이 될 수 없다. v1의 "비율 불일치"는 이 때문이었다(배율 문제가 아니었음).

#### 인식 거리 ∝ 타겟 폭 (2점 확인)

| 추적 폭 | 최대인식 |
|---|---|
| 210 mm (v1) | 110 cm |
| 180 mm (v2) | 88 cm |

→ **인식 거리 ≈ 타겟 폭 × 5**. 이 경험칙으로 추정하면:

| 패널 폭 | 예상 인식 거리 |
|---|---|
| 300 mm | ~1.5 m |
| 420 mm | ~2.1 m |
| 600 mm | ~3.0 m |

§2에서 대상 패널이 **30~60cm 폭**이므로 **관람 거리 1.5m에서 인식 성립 가능성이 높다**
(계획서 §4의 핵심 질문에 긍정적 신호). 단 A4 2점 외삽이므로 0-C 실측 필요.

#### 그 외 확인

- **기울기 28°에서도 인식 유지**, 360° 회전 유지, 재획득 정상
- Pose 변동 1.5~3.1 mm (정면·근접) / 9.4 mm (기울임·손각대)
  → 글자 높이 16mm 기준으로도 여유. **SLAM 없이 이미지 타겟 단독으로 충분해 보임**
    (0-B2 조건부 SLAM 게이트는 현재로선 불필요 판정 쪽)

#### ⚠ 획득 거리 ≠ 유지 거리 (중요 정정)

사용자 실측: **"가까이 대서 인식시키고 뒤로 이동하면 계속 잡힌다."**
→ 앞서 기록한 "최대인식 110/88cm"는 **유지(persistence) 거리**였고,
서비스상 결정적인 값은 **초기 획득(detection) 거리**다. 관람객은 효과를 보려면
그 거리까지 다가와야 하기 때문이다.

HUD를 분리했다:
- **획득거리**: `imagefound` 시점 거리 (미인식 → 인식 전환). 최원값도 함께 기록
- **유지최대**: 잡힌 뒤 버티는 최대 거리

0-B/0-C 성공 기준은 **획득 거리** 기준으로 판정해야 한다.

#### 참고: 인식 거리는 조건에 크게 좌우된다

모니터 표시에서는 인식 거리가 짧았으나(반사·모아레·백라이트), **인쇄물에서 뚜렷이
개선**되었다. 따라서 인식 거리 측정은 반드시 인쇄물로 해야 한다.
